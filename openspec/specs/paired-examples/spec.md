# paired-examples Specification

## Purpose
Показывать применение паттернов сравнением двух конечных исполняемых решений без четырёх снимков кода. Abstract Factory использует общие продукты JSON/YAML/TOML. Strategy сравнивает конфигурации с match и настраиваемые объекты с Protocol; единица копирования — вся папка соответствующего примера.

## Requirements

### Requirement: Две реализации Abstract Factory с общими продуктами
Глава Abstract Factory MUST использовать examples/abstract_factory с interfaces.py, formats/{json,yaml,toml}.py, baseline/, pattern/ и test_example.py. Python-файлы и каталоги MUST использовать snake_case. Общие продукты MUST NOT дублироваться. Самостоятельной единицей копирования MUST быть вся папка паттерна; запуск MUST использовать модули baseline.main и pattern.main из неё.

#### Scenario: Независимое копирование
- **WHEN** папка abstract_factory скопирована вне проекта и установлены объявленные зависимости
- **THEN** обе команды и общий набор тестов работают без пакета сборки курса

### Requirement: Реальная запись и чтение
Reader, Writer и SerializationFactory MUST задаваться через Protocol без наследования конкретных реализаций. Клиент write_and_read MUST записывать dict[str, str] и читать результат парой одного формата. JSON MUST использовать json, YAML MUST использовать safe_load/safe_dump из PyYAML, TOML MUST использовать tomllib и tomli-w. Дополнительная валидация и искусственные поля MUST NOT добавляться ради объёма. Документация MUST отличать аннотации и cast от runtime-проверок.

#### Scenario: Сохранение значений
- **WHEN** обе реализации обрабатывают словарь строк, включая кавычки, Unicode, пустые строки и переводы строк
- **THEN** каждый формат восстанавливает исходный словарь, не изменяя вход

#### Scenario: Подстановка семейства
- **WHEN** клиент с паттерном получает новую структурно совместимую фабрику
- **THEN** он создаёт оба продукта через неё и передаёт результат Writer.write в Reader.read без перечисления форматов

### Requirement: Объяснение расширения без копий состояний
Обе реализации MUST включать JSON/YAML/TOML. Глава MUST объяснять добавление TOML короткими фрагментами конечных исполняемых исходников, перечисляя все изменённые файлы и стабильный клиент. Полный просмотр MUST иметь две версии и общие исходники, без base/extended и фиктивного diff расширения. Старые URL с id abstract-factory MUST сохранять доступ к главе; вложенные пути файлов MUST корректно кодироваться в ссылках.

#### Scenario: Чтение полной реализации
- **WHEN** открыта глава Abstract Factory
- **THEN** доступны baseline и pattern, общие модули показаны один раз, отсутствуют переключатели снимков расширения

#### Scenario: Прежняя ссылка
- **WHEN** читатель открывает старую расширенную ссылку или ссылку formats/toml.py
- **THEN** открывается соответствующая конечная реализация без ошибки и потери пути файла

### Requirement: Исполняемое расширение новым типом продукта
Abstract Factory MUST показывать оба направления расширения: семейство TOML и тип продукта Validator. Validator MUST иметь Protocol validate(text: str) -> None и реализации JsonValidator/YamlValidator/TomlValidator в общих formats/*.py. SerializationFactory и каждая конкретная фабрика MUST предоставлять create_validator. Общая проверка структуры MUST находиться в validation.py без дублирования между форматами.

#### Scenario: Проверка входного текста
- **WHEN** validate_and_read получает текст JSON/YAML/TOML
- **THEN** соответствующий Validator проверяет синтаксис и словарь со строковыми ключами и значениями, затем Reader возвращает данные

#### Scenario: Ошибка данных
- **WHEN** текст имеет неверный синтаксис или нарушает контракт словаря строк
- **THEN** обе реализации выбрасывают соответствующую ошибку библиотеки либо ValueError для структуры; чтение после отказа Validator не выполняется

#### Scenario: Сохранение прежнего сценария
- **WHEN** добавлен Validator
- **THEN** прежний write_and_read сохраняет код и поведение, а новый validate_and_read реализован в baseline и pattern

### Requirement: Два направления роста в главе
Глава Abstract Factory MUST содержать три парных сравнения из исполняемых исходников: запись/чтение, семейство TOML, тип продукта Validator. Фрагменты MUST сохранять ограничение12 непустых строк. Объяснение MUST перечислять изменённые интерфейсы, все фабрики и новый клиент, отличая их от неизменного write_and_read. Материал MUST прямо объяснять двойной разбор текста при отдельной валидации и чтении и простую альтернативу объединения этих действий. Отдельные base/extended MUST NOT возвращаться.

#### Scenario: Сопоставление расширений
- **WHEN** читатель открывает примеры и полную реализацию
- **THEN** он видит работающие оба направления роста и два конечных решения с общими продуктами, без вымышленных снимков до изменения

### Requirement: Две конечные реализации Strategy
Strategy MUST использовать baseline/{operations,context,main}.py, pattern/{interfaces,strategies,context,main}.py и общий test_example.py. Самостоятельной единицей копирования MUST быть вся папка examples/strategy. Запуск MUST использовать модули baseline.main и pattern.main. Обе версии MUST включать Add(amount), Multiply(factor), Constant(value), без base/extended и искусственных общих обёрток.

#### Scenario: Независимый запуск
- **WHEN** папка Strategy скопирована вне курса
- **THEN** обе модульные команды и общий тест работают без пакета сборки

### Requirement: Настраиваемый алгоритм и стабильный клиент
В baseline конфигурации MUST быть dataclass, Context.operation MUST иметь закрытое объединение типов, а apply_all MUST выбирать вычисление через match. В pattern Strategy MUST быть Protocol с apply(int)->int; Add/Multiply/Constant MUST быть frozen dataclass без наследования, Context MUST хранить текущую стратегию и обходить список через её метод. Входные списки MUST NOT изменяться.

#### Scenario: Одинаковые возможности
- **WHEN** обе версии получают [1,2,3] и последовательно Add(2), Multiply(4), Constant(7)
- **THEN** обе дают [3,4,5], [4,8,12], [7,7,7], сохраняя один экземпляр Context и исходный список

#### Scenario: Разные настройки
- **WHEN** выбраны Add(2) и Add(10)
- **THEN** результат определяется конфигурацией соответствующего экземпляра

#### Scenario: Внешняя стратегия
- **WHEN** передан внешний объект с совместимым apply без наследования
- **THEN** pattern Context выполняет его без изменения списка известных типов

### Requirement: Честный разбор расширения Strategy
Глава MUST сравнивать match и делегирование через Protocol, объяснять добавление Constant, замену стратегии и цену смены контракта. Два коротких сравнения MUST извлекаться из конечных исходников и сохранять предел12 непустых строк. Глава MUST объяснять более короткую альтернативу с функцией и MUST NOT обещать, что смена операции доступна только с паттерном. Старые ссылки MUST сохранять сторону и смысловую пару.

#### Scenario: Добавление Constant
- **WHEN** читатель изучает расширение
- **THEN** видит новую конфигурацию, расширение объединения и ветку match в baseline, новую реализацию в pattern и стабильные Strategy/Context

#### Scenario: Изменение контракта
- **WHEN** алгоритму требуется дополнительный обязательный аргумент
- **THEN** текст объясняет необходимость изменить контракт, реализации и вызывающий код

#### Scenario: Прежняя расширенная ссылка
- **WHEN** открыта Strategy v3 или extended/growth-1
- **THEN** v3 сохраняет baseline, а growth-1 открывает пару конфигураций и стратегий конечного примера
