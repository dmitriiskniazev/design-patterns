# project-workflow Specification

## Purpose
Обеспечить единое ведение изменений учебного проекта в OpenSpec с актуальными требованиями, планом задач и сохранёнными результатами проверок, без конкурирующих каталогов планирования.

## Requirements

### Requirement: Единый процесс изменений
Проект MUST вести принятые требования в openspec/specs, активные изменения в openspec/changes и завершённые изменения в его архиве. Новое изменение MUST содержать предложение, требуемые спецификации, план и проверяемые задачи.

#### Scenario: Продолжение разработки
- **WHEN** начинается изменение курса или интерфейса
- **THEN** его область и состояние определяются документами OpenSpec

### Requirement: Перенос истории и безопасная очистка
При смене процесса проект MUST сохранять принятый контракт и имеющиеся результаты проверок, отделять исторические результаты от текущего исполнения и сохранять резервную копию удаляемых авторских документов. После переноса MUST отсутствовать активные каталоги Spec Kit и Kiro/cc-sdd.

#### Scenario: Завершённый перенос
- **WHEN** миграция завершена
- **THEN** текущие требования и результаты доступны в OpenSpec, устаревшие рабочие каталоги удалены, а исходники курса и AGENTS.md сохранены

### Requirement: Запуск через uv
Проект MUST содержать pyproject.toml, uv.lock, пакет в src и инфраструктурные проверки в tests. Python-примеры, тесты, сборка и локальный сервер MUST запускаться через uv с выбранным Python 3.15 или новее. Команды в учебных материалах MUST показывать запуск через uv. Проект MUST NOT требовать make или содержать Makefile. Скачиваемые учебные комплекты MUST запускаться без установки пакета курса.

#### Scenario: Запуск примера
- **WHEN** пользователь запускает указанную команду базового или расширенного примера
- **THEN** uv выбирает требуемый Python, и пример выполняется

#### Scenario: Проверка и просмотр курса
- **WHEN** пользователь запускает указанную uv-команду тестов, сборки или локального сервера
- **THEN** Python-команда выполняется без make

#### Scenario: Скачанный пример
- **WHEN** пользователь распаковывает комплект и выполняет указанную команду
- **THEN** пример или его тесты запускаются через uv независимо от пакета курса

### Requirement: Проверка полного набора
Документированная общая команда проверки MUST находить все каталоги учебных примеров и запускать их pytest-проверки через uv отдельными процессами, прекращая проверку при первой ошибке. Новая тема MUST NOT требовать ручного добавления в список запуска.

#### Scenario: Новая тема
- **WHEN** добавлен каталог examples/<pattern>/python с test_*.py
- **THEN** общая команда проверяет его вместе с остальными темами без конфликтов одноименных модулей

### Requirement: Проверка исполняемых сравнений
Инфраструктурная проверка MUST собирать четыре версии каждой темы сравнения в независимых временных папках и запускать их отдельными Python-процессами. Показанный код MUST совпадать с запущенными файлами. Обе стороны MUST выдавать ожидаемый одинаковый результат. Расширения MUST накладывать изменённые файлы на базовые без скрытых импортов из другой версии.

#### Scenario: Самостоятельные версии
- **WHEN** выполняется test-course
- **THEN** проверяются базовые и расширенные решения без паттерна и с паттерном всех тем с comparison-метаданными

### Requirement: Независимая приемка качества
Существенная ревизия курса MUST проходить независимое ревью контента, кода и структуры по фиксированной шкале 100 баллов для каждого направления. Каждый вычет MUST иметь конкретное обоснование и ссылку; критические и существенные дефекты MUST быть устранены независимо от итогового балла. Приемка MUST требовать не менее 95 баллов в каждом направлении и успешных проверок; ограничения проверки MUST быть перечислены.

#### Scenario: Повторное ревью
- **WHEN** исправления завершены
- **THEN** ревьюер, не автор проверяемых исправлений, повторно проверяет материал по той же шкале и фиксирует результат
