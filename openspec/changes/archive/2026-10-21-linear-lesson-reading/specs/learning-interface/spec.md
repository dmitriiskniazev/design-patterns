## MODIFIED Requirements

### Requirement: Разделы и постоянные ссылки
Интерфейс MUST вести читателя по единой последовательности: задача и мотивация, базовое решение по шагам, самостоятельная практика, расширенное решение по шагам, следующая готовая тема. На каждом экране MUST быть один следующий переход и обратный переход, кроме границ курса. Прогресс MUST показывать положение в этой последовательности. Вкладки разделов, список переходов между шагами и переходы из схемы MUST NOT конкурировать с основным чтением. Прямые ссылки MUST сохранять тему, раздел и шаг; история браузера MUST работать. Выбор темы в каталоге MUST открывать её начало.

#### Scenario: Возврат к разделу
- **WHEN** открывается ссылка готового урока или используется история браузера
- **THEN** восстанавливаются выбранные тема, раздел и шаг

#### Scenario: Ошибочная ссылка
- **WHEN** идентификатор темы или формат ссылки некорректен
- **THEN** интерфейс открывает доступный материал Strategy без ошибки выполнения

#### Scenario: Конец расширения
- **WHEN** пользователь завершает последний шаг расширения
- **THEN** следующий переход открывает начало следующей готовой темы, а после последней темы показано завершение курса без возврата к практике

#### Scenario: Начало другой темы
- **WHEN** пользователь выбирает другую тему из каталога, находясь на шаге расширения
- **THEN** открывается постановка новой темы, а не расширение


### Requirement: Собранный код доступен для чтения
Пользователь MUST иметь возможность посмотреть полный итоговый комплект Python-файлов на странице отдельно от коротких шагов. Показанный текст MUST совпадать с соответствующим файлом скачиваемого исполняемого комплекта; код MUST соответствовать предметной теме урока и поддерживать локальное чтение. Полный код MUST показываться по явному выбору пользователя.

#### Scenario: Чтение итогового файла
- **WHEN** пользователь выбирает просмотр собранного кода
- **THEN** после последнего шага соответствующего разбора раскрывает последовательный список файлов с их обязанностями и подсвеченным кодом; закрытие списка возвращает компактный показ шага

#### Scenario: Сохранение постепенного формата
- **WHEN** пользователь открывает шаг без выбора полного файла
- **THEN** отображается один короткий листинг с контекстом, а полный код файлов не показывается автоматически

### Requirement: Ограниченная предметная область
Каждый урок MUST использовать подходящую паттерну узнаваемую задачу. Strategy MUST показывать поведение игрового противника, Adapter — согласование звуковых API, State — проигрыватель, Command — редактор с отменой, Observer — датчики станции, Composite — дерево игровой сцены, Decorator — звуковые эффекты. Каждый разбор MUST ограничивать дополнительные предметные правила теми, которые непосредственно объясняют паттерн. Расширение MUST добавлять одну возможность. Файлы данных, реализации и запуска MUST быть разделены по обязанностям и доступны для чтения в комплекте.

#### Scenario: Общая тема без лишних правил
- **WHEN** пользователь изучает три готовых урока
- **THEN** видит разные небольшие задачи и понимает выбор поведения противника, согласование звуковых API и состояния проигрывателя без посторонних предметных процессов

#### Scenario: Чтение и запуск файлов
- **WHEN** пользователь выбирает полный пример или скачивает его
- **THEN** может последовательно читать файлы с указанными обязанностями и получает все файлы, необходимые для документированной uv-команды

### Requirement: Общая картина решения
Каждый готовый базовый и расширенный разбор MUST предоставлять схему участников с обязанностями, связями и конкретным примером выполнения. Каждый короткий фрагмент MUST объяснять своё место в этой схеме. Схема MUST показываться один раз после идеи паттерна в базовой части и перед первым расширенным шагом. При прямом открытии другого шага его пояснение MUST называть соответствующий файл и обязанность; схема MUST NOT создавать отдельные переходы между шагами.

#### Scenario: Изучение частей в контексте
- **WHEN** пользователь открывает разбор или отдельный шаг
- **THEN** видит схему в начале разбора и пояснение места текущего листинга на каждом шаге; может проследить конкретный вызов при последовательном чтении

#### Scenario: Переход от схемы к коду
- **WHEN** пользователь прочитал схему и продолжает разбор
- **THEN** следующий переход ведёт к первому шагу, а последующие шаги указывают своё место в схеме

## ADDED Requirements

### Requirement: Последовательное изложение урока
Теория MUST излагаться одной колонкой в порядке: задача, простое решение, новое требование, идея паттерна, участники и путь вызова, условия применения и цена. Схема MUST следовать после мотивации, не повторяться на каждом базовом шаге и не вводить переходов между шагами. Дублирующий список ролей и предварительный первый листинг MUST NOT разрывать этот порядок. Каждый экран кода MUST сохранять один короткий листинг и пояснение его места. Итоговый комплект и просмотр полных файлов MUST предлагаться после последнего шага соответствующего разбора.

#### Scenario: Первое чтение любой темы
- **WHEN** пользователь последовательно проходит готовый урок
- **THEN** сначала узнаёт задачу и причину изменения, затем схему и шаги реализации, выполняет задание и только после него переходит к разбору расширения

#### Scenario: Прямой вход в код
- **WHEN** пользователь открывает первый базовый или расширенный шаг по ссылке
- **THEN** видит постановку перед текущим листингом; дальнейший переход продолжает общий порядок
