## MODIFIED Requirements

### Requirement: Разделы и постоянные ссылки
Интерфейс MUST вести читателя через25 guide-глав по единой последовательности. В каждой главе MUST быть разделы задачи и схемы, различий кода, роста требований и применения. Главы MUST иметь один следующий и обратный переход, кроме границ курса; прогресс MUST показывать номер главы. Каталог MUST открывать начало выбранной темы. Прежние ссылки theory/code/extension/practice MUST открывать соответствующую часть одной главы; история браузера MUST работать.

#### Scenario: Возврат к разделу
- **WHEN** открывается ссылка готового урока или используется история браузера
- **THEN** восстанавливаются выбранные тема и место чтения; в всех guide-главах шаг соответствует смысловой части полной страницы

#### Scenario: Ошибочная ссылка
- **WHEN** идентификатор темы или формат ссылки некорректен
- **THEN** интерфейс открывает доступный материал Strategy без ошибки выполнения

#### Scenario: Конец расширения
- **WHEN** пользователь завершает последний шаг расширения
- **THEN** следующий переход открывает начало следующей готовой темы, а после последней темы показано завершение курса без возврата к практике

#### Scenario: Начало другой темы
- **WHEN** пользователь выбирает другую тему из каталога, находясь на шаге расширения
- **THEN** открывается постановка новой темы, а не расширение


### Requirement: Постепенное представление кода
Каждый готовый урок MUST вводить конструкции короткими пояснениями и парными фрагментами не длиннее12 непустых строк. Общие строки MUST показываться один раз. Полные именованные файлы, включая импорты и запуск, MUST быть доступны под закрытыми раскрытиями. Ограничение12 строк относится к поясняющим фрагментам, а не к полным файлам. Интерфейс MUST NOT требовать скачивания.

#### Scenario: Чтение по шагам
- **WHEN** пользователь открывает код и переходит к следующему шагу
- **THEN** в главе отображается следующий короткий листинг; в guide-главе видны короткие фрагменты различий, а полные файлы скрыты под раскрытием

#### Scenario: Отдельный исполняемый файл
- **WHEN** пользователь копирует файлы полного примера
- **THEN** получает исполняемый набор с импортами и точкой запуска


### Requirement: Собранный код доступен для чтения
Пользователь MUST иметь возможность раскрыть полный комплект Python-файлов в конце любой главы. Показанный текст MUST совпадать с исполняемым исходником и поддерживать локальное чтение. Полный код MUST быть скрыт по умолчанию; одинаковые файлы MUST показываться один раз со ссылками из состава версий. Интерфейс MUST NOT предлагать скачивание.

#### Scenario: Чтение итогового файла
- **WHEN** пользователь выбирает просмотр собранного кода
- **THEN** видит полные файлы под раскрытием, включая guide-главы

#### Scenario: Сохранение постепенного формата
- **WHEN** пользователь открывает шаг без выбора полного файла
- **THEN** отображаются короткие фрагменты, а полные файлы остаются скрытыми


### Requirement: Последовательное изложение урока
Все25 готовых тем MUST излагаться одним форматом guide book: задача и инвариант, схема конкретного вызова, парные короткие различия реализации, рост требований, применение и цена. Полные исходники MUST быть скрыты по умолчанию и дедуплицированы. Каждый переход далее MUST вести к следующей теме; прежние пошаговые ссылки MUST вести в соответствующий раздел главы.

#### Scenario: Первое чтение любой темы
- **WHEN** пользователь последовательно проходит готовый урок
- **THEN** сначала узнаёт задачу; затем проходит шаги в главе или сравнивает две реализации и их расширения в теме сравнения

#### Scenario: Прямой вход в код
- **WHEN** пользователь открывает первый базовый или расширенный шаг по ссылке
- **THEN** видит постановку перед текущим листингом; дальнейший переход продолжает общий порядок

### Requirement: Сравнение решений в основном курсе
Все25 готовых тем MUST показывать guide book с формальной постановкой, схемами участников, конкретным вызовом, парными короткими фрагментами различий, направлениями роста и ценой подходов. Общие модели и повторяющиеся файлы MUST NOT дублироваться в основном сравнении. Полные исходники MUST быть доступны в закрытых по умолчанию раскрытиях и повторяться только как ссылки на один текст. На широком экране варианты MUST быть рядом, на узком последовательно. Фрагменты MUST извлекаться из исполняемых исходников; глава MUST явно отличать дополнительные иллюстрации применения от запускаемого примера. Основной вход web/index.html MUST показывать этот формат без скачивания.

#### Scenario: Обычный вход
- **WHEN** читатель выбирает одну из 25 тем
- **THEN** сначала видит задачу и рисунки, затем различия подходов в коротких исходных фрагментах; полные файлы скрыты

#### Scenario: Сравнение реализации
- **WHEN** читатель сравнивает варианты
- **THEN** одинаковые элементы не отвлекают от различий, а имя файла и извлечённый фрагмент показывают место изменения

#### Scenario: Расширение
- **WHEN** читатель изучает расширяемость
- **THEN** видит несколько осей роста, неизбежные изменения подключения и проверки, а также случай, когда простой вариант удобнее

### Requirement: Проверяемая guide-глава
Сборка MUST требовать ровно одну guide-главу для каждой готовой темы и отклонять пропуски, неизвестные темы и дубли. Сборка MUST извлекать каждый сравниваемый фрагмент из существующего Python-файла, ограничивать его 12 непустыми строками, проверять ссылки схем и сохранять все полные файлы с указанием вариантов использования. SVG MUST иметь доступное текстовое описание. Guide-главы MUST сохранять последовательную навигацию между темами и совместимость прежних ссылок.

#### Scenario: Недостоверный фрагмент
- **WHEN** selector не найден, путь выходит из проекта или схема ссылается на неизвестный узел
- **THEN** сборка завершается ошибкой вместо публикации недостоверного сравнения

## ADDED Requirements

### Requirement: Термины и причины дизайна
Каждая глава MUST до сравнений кратко объяснять употребляемые специальные термины, включая клиент, SDK и контракт там, где они используются. Глава MUST объяснять причины границ объектов и классов, а не только их обязанности. Закрытые наборы вариантов MUST использовать StrEnum вместо строковых литералов выбора. Свободные текстовые данные MUST оставаться строками. Сравнение Strategy MUST передавать координаты игрока и противника явными параметрами без отдельного Positions.

#### Scenario: Чтение Adapter
- **WHEN** читатель открывает Adapter
- **THEN** видит определения SDK и клиента, причину выделения адаптера и одинаковый вызов клиентов

#### Scenario: Чтение Strategy
- **WHEN** читатель сравнивает движение
- **THEN** различает собственную позицию Enemy и входную координату игрока, видит Behavior и причину передачи Move

### Requirement: Различимые листинги
Парные листинги MUST сохранять прежнюю палитру подсветки, использовать шрифт не менее14px при стандартном размере текста, межстрочный интервал не менее1.8 и различимые границы вариантов. Общие строки MUST иметь явную подпись и не снижать читаемость прозрачностью.

#### Scenario: Сравнение кода
- **WHEN** читатель сравнивает реализации
- **THEN** видит подписанные отдельные панели, а общие строки выделены отдельным блоком без дублирования
